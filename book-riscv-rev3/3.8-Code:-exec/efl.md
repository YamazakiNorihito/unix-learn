## ELF Header（`readelf -h`の出力）

| 項目 | 値 | 説明 |
|------|-----|------|
| **Magic** | `7f 45 4c 46 02 01 01 00...` | ELFファイルの識別子。`7f 45 4c 46`は".ELF"を表し、以降はクラス(64bit)、エンディアン等を示す |
| **Class** | ELF64 | 64ビット形式のELFファイル |
| **Data** | 2's complement, little endian | データ表現形式。2の補数、リトルエンディアン |
| **Version** | 1 (current) | ELFフォーマットのバージョン |
| **OS/ABI** | UNIX - System V | 対象OS/ABI（Application Binary Interface） |
| **ABI Version** | 0 | ABIのバージョン |
| **Type** | EXEC | ファイル種別。EXEC=実行可能ファイル |
| **Machine** | RISC-V | ターゲットアーキテクチャ |
| **Version** | 0x1 | オブジェクトファイルのバージョン |
| **Entry point address** | 0xbc | プログラム実行開始アドレス |
| **Start of program headers** | 64 bytes | プログラムヘッダテーブルのファイル先頭からのオフセット |
| **Start of section headers** | 36216 bytes | セクションヘッダテーブルのオフセット |
| **Flags** | 0x5, RVC, double-float ABI | アーキテクチャ固有フラグ。RVC=圧縮命令対応 |
| **Size of this header** | 64 bytes | ELFヘッダ自体のサイズ |
| **Size of program headers** | 56 bytes | 各プログラムヘッダのサイズ |
| **Number of program headers** | 4 | プログラムヘッダの数 |
| **Size of section headers** | 64 bytes | 各セクションヘッダのサイズ |
| **Number of section headers** | 18 | セクションヘッダの数 |
| **Section header string table index** | 17 | セクション名文字列テーブルのインデックス |

## Program Header（`objdump -p`の出力）

各プログラムヘッダは実行時にメモリにロードされるセグメントを定義します：

| フィールド | 説明 |
|-----------|------|
| **off** | ファイル内オフセット（セグメントデータの開始位置） |
| **vaddr** | 仮想アドレス（メモリ上にロードされるアドレス） |
| **paddr** | 物理アドレス（通常はvaddrと同じ） |
| **align** | アライメント要件（2^N バイト境界） |
| **filesz** | ファイル内でのセグメントサイズ |
| **memsz** | メモリ上でのセグメントサイズ（fileszより大きい場合、残りは0で埋められる=BSS領域） |
| **flags** | アクセス権限：`r`=読み取り、`w`=書き込み、`x`=実行 |

### 各セグメントの役割

| セグメント | flags | 役割 |
|-----------|-------|------|
| **0x70000003** (RISC-V属性) | r-- | RISC-V固有のメタデータ |
| **LOAD** | r-x | コード領域（`.text`）。実行可能、読み取り専用 |
| **LOAD** | rw- | データ領域（`.data`, `.bss`）。読み書き可能。`memsz > filesz`なのでBSS領域を含む |
| **STACK** | rw- | スタック領域の定義（サイズ0はランタイムで決定される意味） |

### 用語の分かりやすい説明

各フィールドの意味を、たとえを使って説明します。

#### off（オフセット）とは？

**「ファイルの先頭から何バイト目にデータがあるか」** を示す数値です。

```
user/_init ファイルの中身（イメージ）:

ファイル先頭
↓
[0バイト目]─────────────────────────────────────────→[ファイル末尾]
     │
     │  off = 0x1000 (4096) の場合
     │  ↓
     └──[4096バイト目から、このセグメントのデータが始まる]
```

本に例えると「この章は100ページ目から始まります」という情報です。

#### filesz（ファイルサイズ）とは？

**「このセグメント（部品）だけのサイズ」** です。user/_initファイル全体のサイズではありません。

```
user/_init ファイル全体の構成:

┌─────────────────────────────────────────────────┐
│ ELFヘッダ (64バイト)                              │
├─────────────────────────────────────────────────┤
│ プログラムヘッダテーブル                          │
├─────────────────────────────────────────────────┤
│ セグメント1: コード (.text)   ← filesz = 2561バイト │
├─────────────────────────────────────────────────┤
│ セグメント2: データ (.data)   ← filesz = 16バイト   │
├─────────────────────────────────────────────────┤
│ その他のセクション...                             │
└─────────────────────────────────────────────────┘
```

#### align（アライメント）とは？

**「メモリに配置するときの位置ルール」** です。

`align 2**12` は「2の12乗 = 4096バイト境界に配置する」という意味です。

```
メモリアドレス:
0x0000 ← 4096で割り切れる (OK)
0x0001 ← 4096で割り切れない (NG)
0x0002 ← 4096で割り切れない (NG)
  ...
0x1000 (=4096)  ← 4096で割り切れる (OK)
0x2000 (=8192)  ← 4096で割り切れる (OK)
0x3000 (=12288) ← 4096で割り切れる (OK)
```

**なぜ必要？**
- CPUはメモリを「ページ」単位（通常4KB=4096バイト）で管理する
- ページ境界に揃えると、メモリ保護やキャッシュが効率的に動作する

### 各セグメントの実データ解説

#### 1. 0x70000003（RISC-V属性セグメント）

```
0x70000003 off    0x0000000000007e27 vaddr 0x0000000000000000 paddr 0x0000000000000000 align 2**0
         filesz 0x0000000000000074 memsz 0x0000000000000000 flags r--
```

| フィールド | 値 | 解説 |
|-----------|-----|------|
| **type** | 0x70000003 | RISC-V固有のセグメントタイプ（属性情報） |
| **off** | 0x7e27 (32295) | ファイルの32,295バイト目からこのデータが始まる |
| **vaddr** | 0x0 | メモリにはロードしない（メタデータなので） |
| **paddr** | 0x0 | 物理アドレスも0（使わない） |
| **align** | 2^0 = 1 | どこに置いてもOK（位置制約なし） |
| **filesz** | 0x74 (116バイト) | この属性データは116バイト |
| **memsz** | 0x0 | メモリには0バイト確保（実行時に使わない） |
| **flags** | r-- | 読み取り専用 |

**このセグメントの目的:**

このセグメントには **RISC-V固有の属性情報** が格納されています：

```
格納されている情報の例:
- ISA拡張: RV64GC（64bit、圧縮命令対応、浮動小数点対応）
- ABI: double-float（倍精度浮動小数点を使用）
- スタックアライメント要件
```

**なぜ必要か？**

| 用途 | 説明 |
|------|------|
| **リンク時の互換性チェック** | 異なるオプションでコンパイルされたコードを結合するとき、互換性があるか確認する。例：32bit用と64bit用のコードを誤って混ぜないようにする |
| **実行環境の検証** | プログラムが必要とするCPU機能（浮動小数点演算、圧縮命令など）をチェック。対応していないCPUで実行しようとするとエラーにできる |
| **デバッグ・解析ツール用** | readelfやobjdumpが「このバイナリはどのRISC-V拡張を使っているか」を表示するために使う |

**重要**: `memsz = 0` なので、プログラム実行時にはメモリにロードされません。あくまで「メタデータ」として存在するだけです。

#### 2. LOAD（コード領域 .text）

```
    LOAD off    0x0000000000001000 vaddr 0x0000000000000000 paddr 0x0000000000000000 align 2**12
         filesz 0x0000000000000a01 memsz 0x0000000000000a01 flags r-x
```

| フィールド | 値 | 解説 |
|-----------|-----|------|
| **type** | LOAD | メモリにロードされるセグメント |
| **off** | 0x1000 (4096) | ファイル内4096バイト目から開始（ページ境界） |
| **vaddr** | 0x0 | 仮想アドレス0番地にロード（プログラムの開始位置） |
| **paddr** | 0x0 | 物理アドレス（vaddrと同じ） |
| **align** | 2^12 = 4096 | 4KBページ境界アライメント |
| **filesz** | 0xa01 (2561バイト) | コードのファイル内サイズ |
| **memsz** | 0xa01 (2561バイト) | メモリ上サイズ（filesz=memszなのでBSSなし） |
| **flags** | r-x | 読み取り・実行可能（書き込み不可） |

**補足**: Entry point address (0xbc) はこのセグメント内にあり、vaddr 0x0 + 0xbc = 0xbc が実行開始位置。

#### 3. LOAD（データ領域 .data/.bss）

```
    LOAD off    0x0000000000002000 vaddr 0x0000000000001000 paddr 0x0000000000001000 align 2**12
         filesz 0x0000000000000010 memsz 0x0000000000000030 flags rw-
```

| フィールド | 値 | 解説 |
|-----------|-----|------|
| **type** | LOAD | メモリにロードされるセグメント |
| **off** | 0x2000 (8192) | ファイル内8192バイト目から開始 |
| **vaddr** | 0x1000 (4096) | 仮想アドレス4096番地にロード（コードの次のページ） |
| **paddr** | 0x1000 | 物理アドレス（vaddrと同じ） |
| **align** | 2^12 = 4096 | 4KBページ境界アライメント |
| **filesz** | 0x10 (16バイト) | 初期化済みデータ(.data)のサイズ |
| **memsz** | 0x30 (48バイト) | メモリ上の総サイズ |
| **flags** | rw- | 読み書き可能（実行不可） |

**補足**: `memsz - filesz = 48 - 16 = 32バイト` が未初期化データ領域（.bss）。ローダーはこの32バイトを0で初期化する。

#### 4. STACK（スタック領域）

```
   STACK off    0x0000000000000000 vaddr 0x0000000000000000 paddr 0x0000000000000000 align 2**4
         filesz 0x0000000000000000 memsz 0x0000000000000000 flags rw-
```

| フィールド | 値 | 解説 |
|-----------|-----|------|
| **type** | STACK | スタックセグメントの定義 |
| **off** | 0x0 | ファイル内データなし |
| **vaddr** | 0x0 | アドレスはランタイムで決定 |
| **paddr** | 0x0 | 未使用 |
| **align** | 2^4 = 16 | 16バイト境界（RISC-V ABI要件） |
| **filesz** | 0x0 | ファイル内サイズなし |
| **memsz** | 0x0 | サイズはランタイムで動的確保 |
| **flags** | rw- | 読み書き可能（実行不可） |

**なぜLOADは4KBなのにSTACKは16バイト？**

スタックは **2段階で管理** されています：

```
┌─────────────────────────────────────────────────┐
│                  スタック領域                    │
│                                                 │
│   システム（OS/MMU）の視点: 4KB単位で管理        │
│   ┌────────────────────────────────────────┐   │
│   │ 1ページ = 4KB                          │   │
│   │  ┌──────┐                             │   │
│   │  │16byte│ ← スタックフレーム1          │   │
│   │  ├──────┤                             │   │
│   │  │16byte│ ← スタックフレーム2          │   │
│   │  ├──────┤                             │   │
│   │  │16byte│ ← スタックフレーム3          │   │
│   │  ├──────┤                             │   │
│   │  │ ...  │ (4KB ÷ 16byte = 256個入る)  │   │
│   │  └──────┘                             │   │
│   └────────────────────────────────────────┘   │
│                                                 │
│   プログラムの視点: 16バイト単位で使う           │
└─────────────────────────────────────────────────┘
```

| 管理する人 | 単位 | 目的 |
|-----------|------|------|
| **OS/MMU** | 4KB（ページ） | メモリの確保・保護 |
| **プログラム** | 16バイト | 効率的にスタックを使う |

**ポイント**:
- OSはスタック領域を4KB単位のページで確保・管理する
- しかしプログラムはその中を16バイト単位で細かく使う
- 1ページ（4KB）に最大256個のスタックフレームを詰め込める
- もし4KB単位だと、1回の関数呼び出しで4KB使ってしまい超無駄！
